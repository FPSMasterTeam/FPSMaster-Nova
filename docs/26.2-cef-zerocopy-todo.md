## 零拷贝是什么

mcef-nova 在 CEF 线程把 CEF 的 GPU 共享纹理 import 成一个原生 GL 纹理 id(零拷贝,不碰像素)。
Nova 拿到这个 id 后负责把它画到 Minecraft 的 GUI 上。收益范围:仅 Windows/Linux + N/A 卡,主要
利好动画/视频类网页;静态 UI 下 CPU 路径开销很小。

## 26.2 上已解决的三个渲染障碍(见 `AcceleratedBrowserTexture.kt`)

1. **反射构造器签名变了**:26.2 的 `GlTexture` protected ctor 是 9 参
   `(int,String,GpuFormat,int,int,int,int,int,FrameBufferCache)`。`FrameBufferCache` 从
   `RenderSystem.getDevice()`(一个 `GpuDevice` 前端)的私有 `backend` 字段(`GlDevice`)上反射取
   `frameBufferCache()`(public 方法但声明类包私有,invoke 需 `setAccessible`)。

2. **延迟渲染器画不出外部纹理**:26.2 的 GUI 是延迟渲染(`GuiGraphicsExtractor.blit(view,sampler,…)`
   只记录一个 `BlitRenderState`,真正 GL 绘制在 flush 时)。实测:把 mcef 的**外部导入 id** 直接包成
   `GlTexture`/`GlTextureView` 去 blit,能记录进 render state 但 flush 时**采样为空(画不出)**——
   延迟渲染器只采样**设备自建**的纹理。解决:用 **`glCopyImageSubData`** 把导入纹理 GPU 端拷进一张
   `device.createTexture` 的纹理再画(CPU 全程不碰像素)。注意**不能**用 `device.copyTextureToTexture`
   ——它内部走 FBO blit,而 memory-object 导入的纹理**不能作 FBO 颜色附件**,会报
   `GL_INVALID_FRAMEBUFFER_OPERATION(1286)`。

3. **BGRA→RGBA**:固定 blit 管线无 swizzle。对目标(device)纹理设 GL swizzle
   `SWIZZLE_R←BLUE / SWIZZLE_B←RED`,采样时免 shader 得到正确颜色。

4. **上下颠倒**:CEF 的 GPU 共享纹理是 bottom-up(与软件 paint 纹理相反),blit 时翻转 V 坐标
   (`minV=1, maxV=0`)。实测截图从镜像的 "MONO 3DEGREE STUDIOS" 变正为 "MOJANG STUDIOS",证明方向修复生效。

## 顺带修复的两个真实缺陷(`BasicBrowser.kt`)

- **加速支持探测被过早缓存**:mcef 的 `MCEFAccelerationSupport` 在 GL 上下文就绪前探测会失败并把
  `cachedSupport` 缓存为 UNSUPPORTED 整个会话(启动时序抖动 → 加速时有时无)。修复:
  `isAccelerationAvailable()` 首次在 render 线程且 GL caps 就绪时,反射清一次该缓存强制重探测。

## 当前阻塞:CEF/jcef 只投递一帧就停(逐环隔离结论)

从下往上逐环插桩 + 实测,已把失败**精确定位到最上游**:

| 环节 | 结论 |
|---|---|
| Nova 绘制(wrap→copy→swizzle→V-flip) | ✅ 正确,每帧执行,方向正确,无报错 |
| mcef `flushFrame` ready→displayed 提升 | 只提升一次(`displayedAccelTexId` 恒不变) |
| mcef `onAcceleratedPaint`(CEF 回调) | **CEF 只调用 1 次**(全帧 dirty rect),动画页也不再触发 |
| mcef 导入纹理内容(直接回读源纹理) | 稳定不变,永远是首帧 |
| CPU/软件路径(加速关) | ✅ 同一页面持续产帧、颜色正确、完全正常 |

**已排除的 mcef Java 层修复(均实测无效)**:
- **keyed-mutex**:`glAcquireKeyedMutexWin32EXT` 返回 `GL_INVALID_VALUE(1281)` → 该共享纹理**没有** keyed-mutex,不是这个机制。
- **可见性节流**:`browser.setWindowVisibility(true)` 无效,CEF 仍只一帧。
- **持有纹理导致池耗尽**:让 mcef 导入后立即 `glCopyImageSubData` 到自有纹理并删掉导入纹理(归还
  CEF),CEF 仍只一帧(`onAcceleratedPaint` 计数恒 1)。

**结论**:CEF/jcef 的**原生加速 OSR 帧生产**只产一帧就停,在 mcef 的 Java 层和 Nova 层都改不动。
这很可能是当前 jcef 构建的 bug,或本次验证机器(远程虚拟化 + 混合显卡 NVIDIA/AMD/虚拟显示适配器)
特有。需要在 CEF/jcef 原生侧(C++)或真实单显卡物理机上进一步排查。

## 怎么继续(后续)

1. 在**真实单显卡物理机**(非虚拟化远程)上跑加速路径,确认是否仍只一帧——区分"jcef bug"与"环境"。
2. 若是 jcef bug:在 mcef-nova 的 java-cef 原生侧排查 `OnAcceleratedPaint` 帧调度/共享纹理生命周期;
   或尝试 `external_begin_frame_enabled` + 每帧 `sendExternalBeginFrame()` 驱动(需改 mcef 浏览器创建)。
3. CEF 帧投递修好后,本文档记录的 Nova 渲染管线**无需再改**即可正常显示(管线已就绪),届时把
   `hardware-acceleration` 从 opt-in 提为可默认。
