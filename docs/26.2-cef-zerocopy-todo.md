> windowless_frame_rate(跟随游戏帧率上限)连续渲染,颜色、方向均正确。
> `hardware-acceleration` 仍为 **opt-in 且默认关闭**(beta;开关重启后生效)。
>

> - `src/main/kotlin/top/fpsmaster/web/cef/AcceleratedBrowserTexture.kt`(加速纹理桥)
> - `src/main/kotlin/top/fpsmaster/web/cef/ClientBrowser.kt`(render 分支)

## 两个真正的根因(此前长期互相掩盖)

### 1. CEF 加速 OSR 一帧停摆 → 线程模型问题

mcef-nova 曾把 CEF 消息循环放在专用线程(`CefMessageLoopThread`),并用第二个共享 GL 上下文在
CEF 线程内导入共享纹理。该模型下 CEF 原生加速 OSR **只投递一次 `onAcceleratedPaint` 就停摆**
(keyed-mutex / 可见性 / 纹理归还三种修法均实测无效)。

**修复**:参考 LiquidBounce(CCBlueX/mcef,与 mcef-nova 同源同 jcef commit、同 CEF 143 natives,
其 Accelerated BETA 已上线)的模型——**CEF 消息循环逐帧泵在渲染线程**,`onAcceleratedPaint`
直接在渲染线程、Minecraft 主 GL 上下文内导入。切到该模型后 `onAcceleratedPaint` 以 ~120/s
持续投递(单次实测 20 万+ 次无停摆)。

落地方式:mcef-nova 增加 `-Dmcef.pumpOnRenderThread=true`(CefHelper 走 macOS 式内联初始化,
`MCEF.update()` 每帧 `N_DoMessageLoopWork`);Nova 的 `Client.configureHost` 在 CEF init 前按
`hardware-acceleration` 配置设置该属性。`MCEFBrowserSettings` 将 `shared_texture_enabled`
门控为"仅渲染线程泵模式"——专用线程模式下强制 CPU 路径,避免一帧停摆再次出现。
CEF 线程侧共享 GL 上下文方案(MCEFGlContext)已从 mcef-nova 删除。

代价:加速开启时渲染线程重新承担 CEF 泵(历史上空闲页面有 ~13ms/帧 的定时器量化开销,即
"打开 GUI 前 40fps" 问题);加速关闭(默认)时仍用专用线程,无此开销。

### 2. 26.2/1.21.x `GlTexture` 反射包装参数传反 → 黑屏/假帧

`GlTexture` 的 protected 构造器是 **`(int usage, String label, GpuFormat/TextureFormat, int w,
int h, int depthOrLayers, int mipLevels, int glId[, FrameBufferCache])`——usage 第一、被包装的
GL id 第 8 个**(经 1.21.8/1.21.11 `GlDevice.createTexture` 字节码与 LiquidBounce
`DirectGlTexture.super()` 双重证实)。此前把 texId 传成了 usage、usage(=6)传成了 glId,
导致拷贝源一直是 MC 自己的 6 号纹理——**之前"加速路径显示 Mojang splash"从来不是 CEF 帧**,
也因此当时误判"CEF 纹理 bottom-up 需要 V-flip"。26.2(9 参)与 1.21.5+(8 参)两个分支均已修正。

**方向结论(对真实 CEF 帧截图验证)**:CEF 共享纹理是 **top-down**,与软件 paint 纹理一致,
**不需要 V-flip**(blit UV 与 CPU 路径相同)。

## 26.2 渲染桥仍然成立的三件事(`AcceleratedBrowserTexture.kt`)

1. **延迟渲染器只采样设备自建纹理**:外部包装 id 直接 blit 记录进 render state 但 flush 画空。
   解决:`glCopyImageSubData` 把导入纹理 GPU 端拷进 `device.createTexture` 的目标再画
   (**不能**用 `device.copyTextureToTexture`——FBO blit 对 memory-object 导入纹理报 GL 1286)。
2. **BGRA→RGBA**:对目标纹理设 GL swizzle(`R←BLUE`、`B←RED`),免 shader(截图验证:蓝帧为蓝、
   红绿过渡为橙,若 R/B 反了蓝会变红)。
3. **FrameBufferCache**:从 `RenderSystem.getDevice()`(GpuDevice 前端)的私有 `backend` 字段
   (GlDevice,包私有)反射取 `frameBufferCache()`,invoke 需 `setAccessible`。

## 顺带修复(`BasicBrowser.kt`)

- **探测缓存过早固化**:mcef 在 GL 上下文就绪前探测加速支持会把 UNSUPPORTED 缓存整个会话。
  `reprobeAccelerationSupportOnce()` 首次在渲染线程且 GL caps 就绪时反射清缓存重探测。
- **gating 拆分**:`isAccelerationSupported()`(平台能力,决定 ClickGUI 开关可见性)与
  `isAccelerationAvailable()`(本会话可用 = 支持 && 渲染线程泵)。开关中途打开时老实回退
  CPU 路径,重启后生效。

## 同分支已解决的相关回归

- 26.2 使用 Minecraft 自带的 Netty 4.2;1.21.11 同样不再混入 Netty 4.1。旧版节点只按
  Minecraft 的精确 Netty 版本补充缺失的 `netty-codec-http`,避免 WebSocket 握手
  `NoSuchMethodError` 和 ClickGUI 空白。
- `BrowserOwnedTexture` 在复用 BGRA→RGBA scratch buffer 前重置 limit,避免窗口
  grow-shrink-grow 后反复触发 `IndexOutOfBoundsException` 并持续黑屏。
- 加速开关只会在当前平台/GPU 实际支持时将 CEF 消息循环放到渲染线程;
  `glCopyImageSubData` 的 GL error 会禁用加速路径并让浏览器回退到 CPU 渲染。
